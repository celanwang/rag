# 业务检索验收

2026 年 11 月 17 日在 Apple M4 Max、macOS 15.5 上实测。业务环境运行 PostgreSQL 16.15、pgvector 0.8.7 和 Elasticsearch 8.19.16，向量与精排调用阿里云百炼。 [运行手册](../../rag/README.md)

## 电商端到端

- 两个租户通过上传 API 导入四份 Markdown/TXT 样例，完成向量入库和 ES 同步。四种模式均返回本租户证据，引用定位到原文行号，下载内容与上传字节一致。 [电商样例](../samples/ecommerce)
- 在 ES 同步前撤销文档读取权限，候选仍能从 ES 召回，PostgreSQL 复核会拦截。跨租户和已失效的引用或原件返回 `404`。撤销知识库读权限后，检索返回 `403`。
- 实际停止测试 ES 后，`keyword` 返回 `503`。`rrf` 和 `rerank` 标记 `degraded=["keyword"]`，继续从 pgvector 返回经 PostgreSQL 复核的证据。
- 23 项业务集成测试通过，覆盖伪造 ES 候选、精排途中撤权、S3 读取途中撤权、陈旧版本和删除，以及 PostgreSQL 复核不可用时失败。原 PoC 隔离回归也通过。 [检索集成测试](../../tests/test_retrieval.py)

## 原 30 题实测

使用原 14 份文档、30 道题和 35 个证据金标。重新通过业务上传 API 导入，评测 ES 索引仅含这批语料的 60 个切片。两条召回路径各取最多 8 个候选，RRF `k=60`，精排最多取 12 个候选，返回前 5 条。预热后以并发 1 交错跑三轮，每种模式 90 次请求，合计 360 次。各模式的逐题排序在三轮中一致。 [原题集](../../poc/questions.json)

| 模式 | Recall@1 | Recall@3 | Recall@5 | HTTP p50 | HTTP p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| pgvector | 91.7% | 100% | 100% | 168.5 ms | 512.0 ms |
| ES 关键词 | 68.3% | 83.3% | 88.3% | 19.8 ms | 32.9 ms |
| pgvector + ES + RRF | 81.7% | 98.3% | 98.3% | 163.9 ms | 435.6 ms |
| RRF + 百炼精排 | 91.7% | 100% | 100% | 346.6 ms | 538.9 ms |

B15 有两个证据锚点，关键词和 RRF 的前五条各覆盖一个，向量和精排各覆盖两个。向量模式的查询向量化 p50 为 144.1 ms，数据库向量召回 p50 为 6.6 ms。`rerank` 模式的百炼精排阶段 p50 为 179.1 ms。HTTP 延迟包含网络请求和两次证据复核，历史 PoC 的本地 ONNX 模型有不同的运行条件。 [历史 PoC 报告](poc-results.md)

以 50 ms 间隔轮询任务接口，观察到 PG 发布至 ES 可搜的间隔 p50 为 534.2 ms，最大 970.3 ms。该值包含同步 Worker 轮询和 HTTP 状态采样时间。

在固定 `rag-dev` 上复跑时，执行 `uv run --locked --env-file .env python -m rag.dev benchmark --repeat 3`。新一轮的环境清单和逐题结果保存在 `.rag/dev/<run>/`。本报告的原始记录保存在本地 `.rag/benchmark.json`。 [复跑配置](../../rag/README.md#persistent-rag-dev)

## 首轮检索质量优化

2026 年 11 月 17 日在 `rag-dev` 使用业务 API、真实 pgvector、ES 和百炼复跑。原 30 题使用原有 14 份文档及 60 个切片。首批 8 道 bad case 使用原语料和 4 份政策样例，共 65 个切片。两个题集各跑四种模式，每种模式三轮。每路最多召回 8 个候选，精排最多取 12 个，返回前 5 条。前后核对了题集与文档的 SHA-256。首批 8 题可从提交 `b404b39` 读取。 [原题集](../../poc/questions.json) · [现行 bad case 题集](../../rag/benchmark_cases/questions.json)

### B15 的融合复现与改动

B15 需要回答网关流水的保留期和预发故障的记录要求。改动前，「归档桶保留 45 天」在向量路排第 2，关键词前 8 没有命中。两路共同召回的较低名次候选将该证据挤到融合第 6，连续三轮掉出前 5。「记录请求 ID 与所属区域」三轮均排第 1。

业务 RRF 将 `k` 从 60 调为 1。相邻名次的倒数差增大，使较早命中的单路证据更容易进入前 5。固定原索引和切片 ID，通过真实 API 对 B15 分别复查两种候选预算，改动前后各跑三轮。每组内部的排序一致。 [融合实现](../../rag/retrieval.py#L21) · [B15 回归测试](../../tests/test_retrieval.py#L23)

| 每路候选上限 | 归档证据的关键词排名 | 归档证据的融合排名 | B15 Recall@5 |
| --- | ---: | ---: | ---: |
| 8（基准） | 未入候选 | 6 → 4 | 50% → 100% |
| 50（API 默认） | 9 | 4 → 3 | 100% → 100% |

重新导入语料的完整复跑中，B15 的归档证据三轮都从第 6 升至第 5。前 8 的两个单路第 2 名使用相同的 RRF 分数，并按切片 UUID 决定先后。重新导入生成新版本和切片 ID，因此此处的排序与固定索引对照相差一位。

## 扩展检索回归题集

在首批 8 题上追加 11 道对照题，复用原有 65 个切片。每道变体通过 `variant_of` 关联同组基础题。原 30 题与扩展题集共用 JSON 字段校验和检索评分，沿用各自的语料。报告按切片 ID 记录候选阶段与排序截断阶段各自漏掉的证据，可用 `evidence_sources` 查到对应文档及行号。 [题集](../../rag/benchmark_cases/questions.json) · [运行手册](../../rag/README.md#persistent-rag-dev)

在 `rag-dev` 以每路 8 个候选、精排上限 12、返回 5 条的配置跑了三轮。19 题的 RRF Recall@5 为 93.0%，精排为 100%。

| 题组 | 三轮实测 |
| --- | --- |
| Q01、Q09 与 Q03、Q10 · 错号和歧义 | Q09 缺少症状时，RRF 返回两条相近编号的证据。Q10 明确冷藏生鲜和质量问题后，四种模式均把对应售后规则排在首位。 |
| Q04、Q11、Q12 · 漏召回 | Q04 的出境联系人证据未进 ES 前 8，向量召回后落到融合第 7。Q11 和 Q12 的三条金标均进入 RRF 前 5。 |
| Q06、Q13、Q14 · 融合丢证据 | Q13 仅交换两个子问题的顺序，归档证据从融合第 9 升到第 7，两题仍各缺一条。Q14 明确写出热存储和归档桶后，两条证据均进入 RRF 前 2。 |
| Q15–Q17 · 生效边界 | 在旧版最后一天的 Q15，四种模式均把次日才生效的新版排在首位，旧版仍进入前 5。生效当天和次日的 Q16、Q17 中，RRF 与精排均把新版排在首位。 |
| Q08、Q18 与 Q19 · 来源冲突和替代 | Q18 的两份同级制度都进入 RRF 前 5。Q19 提供明确的政策替代关系时，RRF 与精排均把现行版排在首位。 |

原 30 题也跑完三轮，题集和语料指纹与上次一致。RRF Recall@5 为 100%，Recall@1 为 88.3%。B05 和 B06 的首位同分候选按重导入后的切片 UUID 排序，导致 Recall@1 较上次的 81.7% 波动。原 30 题的 360 条记录位于 `.rag/dev/benchmark-20261117-090451-183f6a/benchmark.json`。
